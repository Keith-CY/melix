# M6.7 KV-Cache Quantization Acceleration

## Goal

Add feature-flagged KV-cache quantization acceleration so memory pressure can be reduced on long-running decode paths with measurable trade-offs.

## Scope

- add runtime policy for KV-cache quantization acceleration
- preserve correctness-first behavior for the default path
- expose metrics for memory reduction and throughput impact

## Files

- update `services/mlx-text-worker-swift/Sources/Core/Inference/`
- update `services/mlx-text-worker-swift/Sources/Core/Runtime/`
- update `services/control-plane-swift/Sources/ModelCatalog/`
- update `apps/macos-menubar/Sources/AppMain/`

## Implementation Notes

- acceleration should remain opt-in and benchmarked
- runtime metrics must distinguish active-path acceleration from storage-boundary quantization
- keep the policy surface compatible with per-model acceleration settings
- probe coverage must land before any TurboQuant kernel or cache optimization work
- the pre-optimization affine q4 baseline must be captured from the same report command used for post-optimization comparison
- active-KV reports should include backend, kernel-path, model-call timing, quantization timing, estimated KV bytes, and memory-savings probes
- real-model helper code must reuse the repository's Phase 8 small-text-model convention instead of duplicating Qwen3.5 fixture resolution
- the shared real-model helper should keep deterministic test fixtures local, while allowing benchmark commands to resolve an existing local Hugging Face cache or managed model path before falling back to the Hub id
- Phase 8 real-model E2E uses `mlx-community/Qwen3.5-0.8B-OptiQ-4bit`; the Swift active-KV pre-optimization baseline currently uses `mlx-community/Qwen3-0.6B-4bit` because the pinned Swift MLXLLM registry does not support `model_type = qwen3_5`
- live Swift MLX model probes must run with a metallib matching the Swift MLX dependency; `MELIX_SWIFT_MLX_METALLIB_PATH` should point at an `mlx_metal` 0.29.1 `mlx.metallib` matching `mlx-swift` 0.29.1 when the Python worker environment carries a newer MLX wheel
- the first post-baseline optimization removes redundant decode-side quantization maintenance calls once the cache is already quantized; the post-run evidence is `docs/metrics/phase2-active-kv-decode-guard-postopt.json`
- `turboquant-q4` must be treated as a release-gated fused profile: it may report a non-fallback kernel path only after model attention actually dispatches the fused decode route, and the release gate must remain failed until real-model throughput overhead is at or below 15 percent
- fallback `turboquant-q4` probes must fail the explicit fused release gate in `swift_worker_direct.active_kv_release_gates.turboquant_fused_decode`; routed probes still fail when `worker_tps_overhead_pct > 15`
- the report CLI supports `--require-fused-turboquant`; use it for fused-kernel candidates, not for the current fallback post-run
- architecture notes for the fused-kernel route live in `docs/architecture/2026-04-18-turboquant-kv-cache-optimization.md`
- the Swift custom Metal feasibility slice is covered by `TurboQuantMetalKernelCapability.runIdentitySmokeKernel(...)`, `TurboQuantMetalKernelCapability.runMSEQ4ValueDecodeSmokeKernel(...)`, `TurboQuantMetalKernelCapability.runMSEQ4FusedAttentionSmokeKernel(...)`, `TurboQuantMetalKernelCapability.runMSEQ4FusedAttentionKernelFromQuantizedState(...)`, `WorkerScaffoldTests.testTurboQuantMetalCapabilityRunsCustomIdentityKernel`, `WorkerScaffoldTests.testTurboQuantMetalCapabilityRunsMSEQ4ValueDecodeKernel`, `WorkerScaffoldTests.testTurboQuantMetalCapabilityRunsMSEQ4FusedAttentionKernel`, `WorkerScaffoldTests.testTurboQuantMetalCapabilityRunsMSEQ4FusedAttentionFromQuantizedKVCacheState`, and `WorkerScaffoldTests.testTurboQuantMetalCapabilityRejectsUnsupportedQuantizedKVCacheStateInputs`; it proves `MLXFast.metalKernel(...)` can compile and dispatch identity, packed-q4 value decode, and one-dispatch packed-q4 score plus softmax plus value work in the text worker target before any TurboQuant runtime path is changed
- `swift_worker_direct.active_kv_fused_candidate_probes.turboquant_q4` records smoke capability separately from runtime evidence and must not be used as release-gate proof by itself
- the second runtime candidate dispatches a fused MSE q4 Metal kernel from live MLXLM `QuantizedKVCache` state when available, falls back to the fixed smoke arrays otherwise, and reports `active_kv_candidate_dispatch_code = 1` after either candidate dispatch runs; it is supporting evidence only
- Melix now vendors `mlx-swift-lm` in `third_party/mlx-swift-lm` and patches `MLXLMCommon.attentionWithCacheUpdate(...)` to try `fusedQ4ScaledDotProductAttention(...)` before upstream affine q4 quantized SDPA for supported one-token q4 affine decode states
- `WorkerScaffoldTests.testTurboQuantRuntimeRouteReportsRoutedAfterFusedAttentionDispatch`, `WorkerScaffoldTests.testVendoredFusedQ4AttentionMatchesQuantizedReferenceForDecodeGQA`, and `WorkerScaffoldTests.testAutoSwiftMLXBackendDecodeReportsTurboQuantFusedRuntimeRoute` cover runtime route promotion only after a real fused attention dispatch counter increments
- Swift worker metrics export `active_kv_runtime_route` and `active_kv_runtime_block_reason` so release-gate evidence can distinguish unsupported cache state, blocked fallback, and actual fused routing
- default Swift runtime keeps fused TurboQuant candidate dispatch disabled unless `MELIX_SWIFT_TURBOQUANT_CANDIDATE_PROBE=1` is set before `scripts/dev_up.sh`; runtime route evidence comes from the vendored attention dispatch counter, not from candidate probes
- the first runtime speedup evidence is `docs/metrics/phase2-active-kv-runtime-speedup-postopt.json`; it proves the default path has `candidate_dispatch_count = 0`, while the release gate stays failed because `active_kv_kernel_path = fallback` and `worker_tps_overhead_pct = 45.76`
- the candidate-check speedup evidence is `docs/metrics/phase2-active-kv-candidate-check-probe-preopt.json` and `docs/metrics/phase2-active-kv-candidate-check-postopt.json`; on the supported live `mlx-community/Qwen3-0.6B-4bit` probe, default `turboquant-q4` candidate eligibility checks dropped from 320 to 0 across five 64-token repeats, while the fused release gate remained failed because `active_kv_kernel_path = fallback` and `worker_tps_overhead_pct = 42.62`
- the terminal model-call cleanup evidence is `docs/metrics/phase2-active-kv-terminal-model-call-preopt.json` and `docs/metrics/phase2-active-kv-terminal-model-call-postopt.json`; the probe adds `active_kv_decode_model_call_count` and the optimization stops prepared decode before computing logits for a token that cannot be emitted after `maxOutputTokens`, dropping default `turboquant-q4` decode model calls from 320 to 315 across five 64-token repeats while the fused release gate remains failed because `active_kv_kernel_path = fallback` and `worker_tps_overhead_pct = 43.55`
- the lazy-eval timing evidence is `docs/metrics/phase2-active-kv-lazy-eval-probe.json`; it adds `active_kv_decode_token_eval_total_us`, `active_kv_decode_token_eval_call_count`, `active_kv_decode_token_eval_avg_us`, and `active_kv_decode_loop_total_us` so Swift MLX lazy graph construction can be separated from the sampling/token materialization step that forces execution. The real-model run reports default `turboquant-q4` release-gate `decode_token_eval_total_us = 6438631`, `decode_loop_total_us = 9497000`, `worker_tps_overhead_pct = 42.37`, and `active_kv_kernel_path = fallback`, so the fused release gate remains blocked.
- the next non-hook runtime speedup keeps `q4` available for explicit affine KV compression, but prevents default `turboquant-q4` from silently paying the affine q4 fallback decode cost while the attention hook is unavailable. Candidate-audit runs keep the old quantized fallback by setting `MELIX_SWIFT_TURBOQUANT_CANDIDATE_PROBE=1`; developers can also set `MELIX_SWIFT_TURBOQUANT_AFFINE_FALLBACK=1` for compatibility probes. The fused release gate must still fail until `active_kv_kernel_path != fallback`, `active_kv_estimated_memory_savings_pct >= 67`, and `worker_tps_overhead_pct <= 15` all hold in the same real-model JSON.
- the blocked-fallback speedup evidence is `docs/metrics/phase2-active-kv-blocked-fallback-speedup-postopt.json`; default `turboquant-q4` no longer quantizes the cache while the attention hook is unavailable, so the real-model run reports `active_kv_quantization_ratio = 0`, `active_kv_estimated_memory_savings_pct = 0.0`, `decode_token_eval_total_us = 4009440`, `decode_loop_total_us = 5473976`, and `worker_tps_overhead_pct = -3.39`. The fused release gate remains failed because `active_kv_kernel_path = fallback`, `active_kv_runtime_route = blocked`, and memory savings are zero.
- GitHub issue [#35](https://github.com/Keith-CY/melix/issues/35) tracks the deferred upstream attention-hook alternative; do not unblock the fused active-KV release gate until a real-model metrics JSON shows both `worker_tps_overhead_pct <= 15` and `active_kv_kernel_path != fallback`
- the vendored runtime evidence is `docs/metrics/phase2-active-kv-vendored-turboquant-runtime.json`; with `mlx-community/Qwen3-0.6B-4bit`, matching Swift MLX 0.29.1 metallib, and no `MELIX_SWIFT_TURBOQUANT_CANDIDATE_PROBE`, it reports `active_kv_kernel_path = tq_mse_single`, `active_kv_runtime_route = routed`, `active_kv_fallback_count = 0`, `active_kv_decode_quantize_total_us = 0`, `active_kv_estimated_memory_savings_pct = 75.0`, and `candidate_dispatch_count = 0`, but the release gate remains failed because `worker_tps_overhead_pct = 68.63`
- the same vendored-runtime probe attempted the repository's Phase 8 Qwen3.5 small-model convention first, but direct Swift MLX load failed with `Unsupported model type: qwen3_5`; keep using Qwen3-0.6B for active-KV real-model metrics until the Swift MLXLLM registry supports Qwen3.5
- the shared-score speedup evidence is `docs/metrics/phase2-active-kv-vendored-turboquant-shared-scores.json`; it keeps `active_kv_kernel_path = tq_mse_single`, `active_kv_runtime_route = routed`, `active_kv_fallback_count = 0`, `active_kv_decode_quantize_total_us = 0`, `active_kv_estimated_memory_savings_pct = 75.0`, and `candidate_dispatch_count = 0`, and improves `worker_tps_overhead_pct` from `68.63` to `60.87`; the release gate remains failed because the threshold is `<= 15`
- the next runtime speedup should optimize the fused Metal work partition beyond the shared-score proof. The current shared-score kernel removes per-output-dimension score recomputation and uses simdgroup partial reductions, but it still materializes and synchronizes a per-token score vector; the next kernel should use tiled score/value work with online softmax before rerunning the release gate

## Acceptance

- KV-cache quantization acceleration can be enabled through explicit policy
- memory and throughput effects are measurable and benchmarked
- optimization work is blocked until the report contains non-`N/A` baseline and affine q4 decode rows plus an affine-vs-baseline comparison
- any later TurboQuant profile must be compared against both baseline and affine q4 using the same probe fields
- true TurboQuant remains incomplete until a post-run JSON shows the TurboQuant profile on a non-fallback fused kernel path with measured throughput overhead improvement
- true TurboQuant remains blocked until `--require-fused-turboquant` exits zero on the fused candidate report
